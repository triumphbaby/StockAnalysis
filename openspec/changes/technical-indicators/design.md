## Context

当前系统已完成股票行情数据获取和K线图展示（迭代1）。技术指标功能将在此基础上添加技术分析能力，帮助用户做出更明智的投资决策。

**当前状态:**
- 后端已有 StockService 和 TushareService
- 前端已有 StockChart 组件使用 ECharts
- 数据库存储历史行情数据
- Redis 缓存热门股票数据

**约束:**
- 需保持现有 API 兼容性
- 指标计算不应显著增加响应时间（目标 <500ms）
- 前端图表性能需支持至少1年数据+多个指标
- 技术栈限制：Python后端，React前端

## Goals / Non-Goals

**Goals:**
- 实现5种核心技术指标计算（MA, MACD, RSI, KDJ, BOLL）
- K线图支持主图叠加（MA, BOLL）和副图展示（MACD, RSI, KDJ）
- 提供指标配置界面，用户可自定义参数
- 检测关键技术信号（金叉/死叉、超买/超卖）
- 缓存计算结果以优化性能

**Non-Goals:**
- 不实现高级指标（如 Ichimoku、Fibonacci）- 将在后续迭代实现
- 不提供自动交易功能 - 仅提供分析和信号提示
- 不实现机器学习预测 - 仅基于传统技术分析
- 不支持自定义指标公式 - 仅支持预定义指标

## Decisions

### Decision 1: 使用 pandas-ta 库进行指标计算

**选择:** 使用 `pandas-ta` 库而非 `TA-Lib`

**理由:**
- pandas-ta 是纯 Python 实现，安装简单（TA-Lib 需要 C 依赖）
- 与现有 pandas DataFrame 完美集成
- 活跃维护且文档完善
- 支持所有需要的指标

**替代方案:**
- TA-Lib: 更快但安装复杂，Windows 环境问题多
- 手动实现: 灵活但需大量测试，容易出错

### Decision 2: API 设计 - 扩展现有端点

**选择:** 在现有 `/api/stocks/{code}/prices` 添加 `indicators` 参数

**API 格式:**
```
GET /api/stocks/{code}/prices?period=1m&indicators=ma_5,ma_20,macd,rsi
```

**理由:**
- 保持 API 简洁，避免端点膨胀
- 可选参数设计，不影响现有调用
- 单次请求返回价格+指标，减少往返

**替代方案:**
- 新端点 `/api/stocks/{code}/indicators`: 需要多次请求，增加延迟
- 合并到股票详情接口: 过于耦合，违反单一职责

### Decision 3: 指标数据缓存策略

**选择:** 使用 Redis 缓存计算结果，键格式：`indicators:{stock_code}:{period}:{indicator_params}`

**缓存策略:**
- TTL: 1小时（交易时间） / 24小时（非交易时间）
- 仅缓存完整计算结果，不缓存中间步骤
- 缓存命中时直接返回，未命中时计算后缓存

**理由:**
- 指标计算密集（尤其是 MACD, KDJ），缓存可提升10-100倍性能
- Redis 足够快，不影响用户体验
- 交易时间内数据变化频繁，需要较短 TTL

**替代方案:**
- 数据库持久化: 写入开销大，查询不够快
- 不缓存: 每次计算耗时过长，用户体验差

### Decision 4: 前端图表架构

**选择:** 改造 StockChart 组件支持动态配置，使用 ECharts grid 实现多子图

**架构:**
```
StockChart
├── 主图 (grid 0): K线 + MA + BOLL
├── 副图1 (grid 1): MACD (DIF, DEA, Histogram)
├── 副图2 (grid 2): RSI
└── 副图3 (grid 3): KDJ
```

**理由:**
- ECharts 原生支持 grid 多子图，无需额外库
- 保持现有组件，减少重构风险
- 动态配置可灵活显示/隐藏子图

**替代方案:**
- 多个独立图表组件: 数据同步复杂，性能差
- 使用 D3.js 自绘: 开发成本高，不如 ECharts 成熟

### Decision 5: 指标配置持久化

**选择:** 使用 localStorage 存储用户指标偏好

**存储格式:**
```json
{
  "stockIndicators": {
    "mainChart": ["ma_5", "ma_20", "boll"],
    "subCharts": {
      "macd": { "enabled": true, "params": {"fast": 12, "slow": 26, "signal": 9} },
      "rsi": { "enabled": true, "params": {"period": 14} },
      "kdj": { "enabled": false }
    }
  }
}
```

**理由:**
- localStorage 简单，无需后端支持
- 跨会话保持用户偏好
- 足够存储配置数据（< 10KB）

**替代方案:**
- 后端用户配置表: 增加复杂度，需要用户认证（迭代8才有）
- Cookie: 容量限制（4KB），不够灵活

### Decision 6: 信号检测实现方式

**选择:** 后端实时计算信号，前端仅负责展示

**流程:**
1. 后端计算指标时同时检测信号
2. 返回信号列表 `signals: [{type, date, price, confidence}]`
3. 前端在图表上标注信号点

**理由:**
- 信号检测逻辑复杂（交叉判断、阈值检测），后端更适合
- 前端只关注展示，保持职责分离
- 信号结果可缓存，提高性能

**替代方案:**
- 前端计算信号: 逻辑重复，维护成本高，且 JS 处理大数据性能差

## Risks / Trade-offs

### Risk 1: 指标计算性能瓶颈
**风险:** 复杂指标（如 MACD）在长周期（1年+）数据上计算可能超时

**缓解措施:**
- 实现渐进式加载：优先返回价格数据，指标异步加载
- 使用 Celery 异步任务处理耗时计算
- 预计算热门股票的常用指标，存入数据库

### Risk 2: 缓存失效策略复杂
**风险:** 交易时间内数据更新频繁，缓存可能返回过期数据

**缓解措施:**
- 缓存键包含时间戳粒度（如每5分钟）
- 提供"强制刷新"选项让用户手动更新
- 监控缓存命中率，动态调整 TTL

### Risk 3: 前端图表渲染性能下降
**风险:** 多个副图+大量数据点可能导致图表卡顿

**缓解措施:**
- ECharts 数据抽样（dataZoom 配置）
- 限制同时显示的指标数量（最多5个）
- 使用 Web Worker 处理大数据量（如果需要）

### Risk 4: 指标参数配置混乱
**风险:** 用户可能设置不合理的参数（如 MA250 但只有100天数据）

**缓解措施:**
- 后端参数验证，返回清晰的错误提示
- 前端提供推荐配置和范围限制
- 数据不足时降级处理（如 MA250 自动改为可用的最大周期）

### Trade-off 1: 准确性 vs 性能
**权衡:** 更高精度的指标计算（如使用 Exponential MA）需要更多计算资源

**决策:** 默认使用标准算法（SMA），提供配置选项让高级用户选择 EMA
**影响:** 99%用户够用，高级用户有选择权

### Trade-off 2: 功能丰富度 vs 界面复杂度
**权衡:** 支持更多指标和参数会增加 UI 复杂度

**决策:** 第一版仅支持5种核心指标，简化配置界面
**影响:** 降低学习成本，后续迭代扩展

## Migration Plan

### Phase 1: 后端实现（3天）
1. 安装 pandas-ta: `pip install pandas-ta`
2. 创建 `app/services/indicator_service.py`
3. 实现 IndicatorCalculator 类和各指标方法
4. 添加单元测试（覆盖率 >85%）
5. 扩展 stocks API 支持 indicators 参数

### Phase 2: 前端实现（2天）
1. 重构 StockChart 组件支持多 grid
2. 创建 IndicatorSelector 组件
3. 实现指标配置逻辑（localStorage）
4. 测试各指标展示效果

### Phase 3: 信号检测（1天）
1. 实现 SignalDetector 类
2. 添加信号检测 API
3. 前端图表标注信号点

### Phase 4: 测试和优化（1天）
1. 集成测试（前后端联调）
2. 性能测试和缓存优化
3. UI/UX 优化

### Rollback Strategy
如果出现严重问题：
1. 后端：indicators 参数为可选，可快速禁用
2. 前端：通过 feature flag 关闭指标功能
3. 数据库：无 schema 变更，无需回滚

### Deployment
1. 后端先部署（向后兼容）
2. 前端部署新版本
3. 清空相关 Redis 缓存确保数据一致性
4. 监控 API 响应时间和错误率

## Open Questions

1. **Q:** 是否需要支持分钟级K线的指标计算？
   **A:** 暂不支持，专注日线级别。分钟线留待后续迭代。

2. **Q:** 信号历史是否需要持久化到数据库？
   **A:** 暂不持久化，每次实时计算。未来可考虑存储用于回测分析。

3. **Q:** 是否提供指标对比功能（如同时查看多只股票的 RSI）？
   **A:** 不在本迭代范围，可作为迭代3或4的功能。

4. **Q:** 移动端（响应式）如何展示多个副图？
   **A:** 移动端默认折叠副图，用户可点击展开。需要 UI 设计支持。
